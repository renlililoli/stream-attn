# Windows and WSL2

## Support policy

SeqAttn remains a Linux package. Windows users should run it through WSL2,
which provides the Linux userspace expected by PyTorch, Triton, the shell
scripts, and the paged-storage implementation.

Use one of these two WSL2 paths:

| Path | Recommended use | Status |
|---|---|---|
| Docker Desktop with the WSL2 backend and Linux CUDA containers | ComfyUI users and reproducible Windows deployments | Preferred Windows path; experimental for large sequences |
| Python virtual environment directly inside an Ubuntu WSL2 distribution | SeqAttn development, tests, and hardware calibration | Preferred Windows developer path |
| Native Windows Python or Windows containers | None | Unsupported |

The Docker and direct-Python paths execute the same Linux SeqAttn package. A
separate Windows implementation is neither required nor desirable while WSL2
meets the runtime contract. This branch is intended to validate and document
that contract before the guidance is merged into `main`; it is not a permanent
Windows-specific code fork.

Native Windows is not currently supported because the repository and release
contract are Linux-only, the physical NVMe path uses POSIX file descriptors
and `O_DIRECT`, and the supported CUDA kernels are built and tested with the
Linux PyTorch/Triton toolchain. Do not silently disable these invariants merely
to make an import succeed on native Windows.

WSL2 is not yet equivalent to the bare-metal Linux reference platform for
SeqAttn's largest workloads. NVIDIA documents a limit on pinned system memory
available to CUDA applications under WSL2. SeqAttn intentionally keeps large
Q/K/V or hidden-state working sets in pinned host memory, so a workload that
runs on bare-metal Linux may fail at allocation or require smaller problem
sizes under WSL2. A Docker Desktop container still runs through WSL2 and does
not remove this limit. Use bare-metal Linux for production-scale long-sequence
work until the intended end-to-end shape has passed the acceptance tests below.

## Recommended user path: Docker Desktop

Use this path when SeqAttn is consumed by the MiniMax-H3 ComfyUI community
package. Docker Desktop must use its WSL2 engine and run Linux containers, not
Windows containers.

1. Install a current NVIDIA Windows display driver with WSL CUDA support.
2. Install WSL2 and an Ubuntu distribution from an elevated PowerShell prompt:

   ```powershell
   wsl --install -d Ubuntu
   wsl --update
   wsl --shutdown
   ```

3. Start Ubuntu once and create the Linux user when prompted.
4. Install Docker Desktop, enable its WSL2 engine, and enable integration for
   that Ubuntu distribution.
5. Verify the distribution and GPU from PowerShell:

   ```powershell
   wsl --list --verbose
   wsl nvidia-smi
   wsl docker version
   ```

6. Clone repositories from an Ubuntu shell into the WSL filesystem, for
   example under `~/src`, rather than under `/mnt/c`:

   ```bash
   mkdir -p ~/src
   cd ~/src
   git clone https://github.com/renlililoli/minimax-h3-seq-chunk-attn.git
   cd minimax-h3-seq-chunk-attn
   ```

7. Follow that community repository's `docker/README.md`. Its pinned Linux
   image owns the tested ComfyUI, PyTorch, CUDA, AIMDO, and SeqAttn versions.
   Run Compose from the Ubuntu shell so bind mounts and build context remain
   on the WSL filesystem.

Do not install a second Linux NVIDIA display driver inside WSL. The Windows
driver exposes the GPU to WSL; the Linux environment needs the compatible CUDA
userspace supplied by PyTorch or the container image.

## Recommended developer path: WSL2 Python

Use a direct WSL2 environment when modifying SeqAttn or calibrating chunk
sizes. This avoids rebuilding the complete ComfyUI image after every core
change while retaining the Linux execution model.

From an Ubuntu shell:

```bash
sudo apt-get update
sudo apt-get install -y git python3-dev python3-venv build-essential

mkdir -p ~/src
cd ~/src
git clone https://github.com/renlililoli/stream-attn.git
cd stream-attn
git switch windows/wsl2-support

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
```

Install a CUDA-enabled PyTorch build that matches the Windows NVIDIA driver by
using the command generated by the official PyTorch installation selector.
Then install SeqAttn without replacing that PyTorch build:

```bash
python -m pip install -e '.[cuda,dev]'
```

Verify the runtime before running model code:

```bash
python - <<'PY'
import platform

import torch
import triton

assert platform.system() == "Linux"
assert torch.cuda.is_available()

device = torch.device("cuda:0")
probe = torch.empty(4096, dtype=torch.bfloat16, pin_memory=True)
copied = probe.to(device, non_blocking=True)
torch.cuda.synchronize(device)

print("kernel:", platform.release())
print("torch:", torch.__version__)
print("torch CUDA:", torch.version.cuda)
print("triton:", triton.__version__)
print("GPU:", torch.cuda.get_device_name(device))
print("compute capability:", torch.cuda.get_device_capability(device))
print("pinned H2D probe:", tuple(copied.shape), copied.dtype)
PY
```

The small probe verifies that pinned transfer works, not that the required
host-memory footprint is available. Before a full denoise, allocate and pin a
representative input working set in an isolated process. Record the requested
bytes and failure mode; do not add retry logic that silently reduces sequence
length, tile count, or precision.

Run CPU coverage first, followed by the CUDA paths relevant to the change:

```bash
pytest -q tests/test_reference.py tests/test_planner.py tests/test_backend.py
pytest -q tests/test_triton.py tests/test_pipeline.py tests/test_dit.py
```

FlashAttention 2, 3, and 4 remain optional. Start with `backend="builtin"` or
`backend="auto"`; install a FlashAttention package only when it explicitly
supports the installed PyTorch, CUDA userspace, Python version, and GPU
architecture.

## Files and storage

Keep the repository, Python environment, compiler caches, model weights, and
high-throughput intermediate data in the WSL Linux filesystem. Accessing files
through `/mnt/c`, `/mnt/d`, or another Windows-mounted drive crosses the WSL
filesystem boundary and is not a valid basis for SeqAttn storage or bandwidth
claims.

The paged API defaults to `direct_io=True`. Treat Direct I/O under WSL2 as
unvalidated until the exact filesystem and backing device pass the repository
round-trip test:

```bash
pytest -q tests/test_nvme.py::test_direct_io_round_trip_when_supported
```

If that test skips or fails because `O_DIRECT` is unavailable, use
`direct_io=False` only for functional development. Do not publish physical
NVMe throughput or bounded-I/O claims from that configuration. A production
NVMe result requires a documented WSL version, Linux filesystem, Windows
storage stack, physical device, and successful Direct I/O validation.

## Memory and performance calibration

Do not reuse the checked-in Linux RTX 5090 Q-chunk result as a Windows default.
WSL2 changes the observable CPU topology, memory placement, virtualization
layer, and storage path. Run `docs/q_chunk_calibration.md` inside the final
deployment environment and record at least:

- Windows version and NVIDIA driver;
- `wsl --version` output and Linux kernel release;
- direct WSL2 Python versus Docker Desktop;
- Docker Desktop version and image digest when applicable;
- GPU name, compute capability, PyTorch, CUDA userspace, and Triton versions;
- repository commit, backend, dtype, head shape, Q/K/V tile settings;
- CPU affinity and the topology visible inside WSL;
- whether data resides in the WSL filesystem or a `/mnt/*` mount.

Run every comparison point in a fresh process. Separate warmup and compilation
from steady measurements, and select `q_chunk_tokens` from the measured
concurrent H2D bandwidth and resident-attention roof in that same environment.

## Known boundaries

- WSL1 is unsupported because it does not provide the required CUDA execution
  path.
- Windows containers are unsupported; Docker Desktop must run Linux
  containers through WSL2.
- Native Windows Python is not a release target, even if CPU reference imports
  happen to work.
- WSL2 has a documented pinned-system-memory limit. Docker Desktop does not
  bypass it, so successful small tests do not establish large-sequence support.
- Direct I/O and physical NVMe performance are not assumed from bare-metal
  Linux results.
- WSL2 benchmark results must not be mixed with bare-metal Linux results in an
  unlabeled table.
- Multi-GPU and cross-request scheduling remain outside SeqAttn's current
  single-GPU scope on every platform.

## Acceptance criteria before merging

The WSL2 support guidance can move to `main` after one physical Windows/NVIDIA
system records all of the following from a clean checkout:

1. A CUDA-enabled PyTorch and Triton import with the pinned-memory H2D probe.
2. CPU reference, planner, backend-selection, Triton, projected-pipeline, and
   DiT tests.
3. One contiguous streaming example with correctness statistics and peak HBM.
4. A pinned-host allocation and one full denoise at the intended maximum
   sequence shape, with process RAM and HBM peaks recorded.
5. One independent Q-chunk calibration sweep in the final WSL2 topology.
6. The ComfyUI community example in its pinned Docker Desktop Linux image.
7. Direct I/O capability recorded as pass, skip, or unsupported without silent
   fallback.
